## Confirmed defects and repair

| Severity | Reproduction and cause | Repair and evidence |
| --- | --- | --- |
| High | Hold A's refresh, install B, resolve A. Original actual helper saves A over B because retries reread storage and delayed saves have no identity guard. Original checkout/portal and Settings portal can similarly redirect a later account using an earlier response. | Capture exact initiating credential, invalidate on storage events, guard every awaited continuation, and serialize page operations/Settings portal requests. No later-account write, redirect or fallback. Actual source cases cover header/body delays, successful and failed responses, sign-out/account replacement, same-byte storage invalidation and duplicate actions. |
| High | Original `onPaymentConfirmed()` shows “Welcome to Pro” and navigates to the app even when every refresh returns free. It treats a URL as payment proof and ignores saved entitlement confirmation. | Show unconfirmed recovery until a same-account server response says Pro and storage accepts the save. Quota, malformed response, outage and authorization failure retain truthful recovery. A free response updates stale cached access; it never confirms a payment. |
| High | Review found token for A paired with cached profile B starts checkout for A while presenting B. A returned token for B paired with response user A could also be saved. | Require decoded `app_metadata.user_id` and `sub` to agree with the displayed/captured user before any request and before saving a refreshed session. This is a client consistency check, not token authentication; the server still verifies the token and session version. Missing/mixed app owners fail closed and show sign-in recovery. |
| Medium | Lost checkout response/reload could change return URLs and lose the server's durable attempt continuity. Existing-completed checkout recovery could be forgotten after reload. | Save an account-and-plan nonce before checkout. Retries/reload reuse exact request parameters; intentional plan changes get a new nonce. `checkout_complete` / `subscription_exists` 409 responses persist awaiting-access recovery and show Check/Manage. `checkout_pending` 503 remains retryable. No checkout starts if its recovery marker cannot be saved. |
| Medium | Stalled headers or body reads leave controls blocked indefinitely; cancellation URL claims no charge without proof. Portal errors can lead back to a purchase chooser without useful context. | Bound headers plus JSON body at 15 seconds, drop late results, and provide explicit retries. Cancel/unknown results make no charge claim. Settings portal failures route to `upgrade.html?manage=1` with Check/Manage recovery. A revoked session has a visible sign-in link; no-web-subscription responses preserve Apple ID guidance. |

## Release and remaining boundaries

This is a reviewable frontend candidate, not a verified public payment journey. No provider purchase, account mutation, payment email, backend cutover or frontend deployment occurred. Real Stripe checkout, webhook timing, portal configuration, cancellation, refund status, Apple-to-web entitlement propagation and live return journeys remain separate owner/provider validation gates. The root's reviewed durable checkout/event writers must follow their own release and cutover evidence; this candidate does not deploy them.

Old in-flight checkout links lacking the new nonce are handled conservatively: no automatic activation; the signed-in user can explicitly check the current plan. Missing or inconsistent app credentials require sign-in rather than sending a token under an unrelated cached profile. Legacy local records are not deleted by these billing changes.
